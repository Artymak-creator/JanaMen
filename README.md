# JanaМен / JanaPost — версия по уточнённому ТЗ

React + TypeScript + Vite + Supabase. Интерфейс использует бело-зелёную палитру. В системе предусмотрены три роли, двухэтапный процесс согласования, оплачиваемый и неоплачиваемый отпуск.

## Что реализовано в клиенте

- **Сотрудник (`employee`)** — создаёт заявки, включая заявки на ежегодный отпуск, и видит статус своей заявки.
- **Руководитель (`manager`)** — создаёт собственные заявки и рассматривает заявки сотрудников, для которых назначен согласующим. При согласовании передаёт заявку в HR; при отказе завершает её.
- **HR (`hr`)** — не создаёт заявки; видит заявки на этапе HR и завершённые заявки, принимает финальное решение и ставит отметку с аккаунтом и временем.
- В заявке на ежегодный отпуск можно выбрать **оплачиваемый** тип либо **без сохранения заработной платы**.
- Для оплачиваемого отпуска показывается остаток дней из профиля сотрудника, считается длительность периода и проверяется доступный остаток.
- При финальном одобрении HR оплачиваемого отпуска база списывает запрошенные дни из остатка в той же транзакции. Неоплачиваемый отпуск баланс оплачиваемых дней не расходует.
- Светлая и тёмная темы доступны; основная палитра обновлена на бело-зелёную.

Дни отпуска сейчас считаются **календарными днями с включением даты начала и окончания**. Если рабочее ТЗ требует считать только рабочие дни или исключать праздничные даты, расчёт надо скорректировать отдельно.

## Перед запуском

> Сделайте резервную копию схемы/данных Supabase перед применением SQL. Не выполняйте миграцию наугад в другом проекте: используйте тот Supabase, где уже хранятся рабочие заявки.

### 1. Примените SQL-миграцию

1. Откройте существующий проект на [Supabase](https://supabase.com/dashboard/).
2. Перейдите в **SQL Editor**.
3. Откройте файл `supabase/20261017_janapost_requirements.sql` из этого проекта, скопируйте содержимое в SQL Editor и выполните.
4. Миграция добавляет необходимые поля и серверную проверку маршрута заявки. Она **заменяет существующие RLS-политики таблицы `public.requests`** новыми правилами для процесса сотрудник → руководитель → HR. Перед выполнением убедитесь, что это соответствует настройкам вашего проекта.

Миграция сохраняет старые значения `requests.status` (`На рассмотрении`, `Одобрена`, `Отклонена`) и отдельно добавляет `workflow_stage`; старые незавершённые заявки считаются ожидающими этапа HR, чтобы не отправлять их назад к руководителю. Она также пересоздаёт RLS-политики `public.profiles`, разрешая клиенту только чтение собственного профиля; это не позволяет через браузер самовольно изменить свою роль, руководителя или баланс дней.

### 2. Назначьте роли и руководителей

Роль нельзя выбирать в самом приложении. Назначайте её через Supabase Dashboard / SQL Editor, используя реальные адреса аккаунтов.

Пример SQL-шаблона — замените адреса на реальные. Сначала зарегистрируйте нужные аккаунты и проверьте их в **Authentication → Users**:

```sql
-- Пример: назначить роль руководителя существующему аккаунту
UPDATE public.profiles
SET role = 'manager'
WHERE user_id = (SELECT id FROM auth.users WHERE email = 'manager@example.com');

-- Пример: назначить сотруднику конкретного руководителя
UPDATE public.profiles
SET manager_id = (
  SELECT user_id FROM public.profiles
  WHERE user_id = (SELECT id FROM auth.users WHERE email = 'manager@example.com')
    AND role = 'manager'
)
WHERE user_id = (SELECT id FROM auth.users WHERE email = 'employee@example.com');

-- Пример: назначить остаток оплачиваемых дней сотруднику.
-- Число ниже только пример; укажите остаток, подтверждённый HR.
UPDATE public.profiles
SET annual_leave_days_remaining = 20
WHERE user_id = (SELECT id FROM auth.users WHERE email = 'employee@example.com');

-- Отдельному аккаунту HR назначается роль hr:
UPDATE public.profiles
SET role = 'hr'
WHERE user_id = (SELECT id FROM auth.users WHERE email = 'hr@example.com');
```

Для каждого сотрудника нужно указать `manager_id` и согласованный остаток оплачиваемых дней в `annual_leave_days_remaining`. Если остаток неизвестен, оставьте его `NULL`: оплачиваемую заявку создать нельзя, пока HR не заполнит баланс. Руководителю можно не назначать `manager_id`; тогда его собственная заявка пойдёт напрямую в HR. Если у руководителя есть вышестоящий руководитель, `manager_id` может ссылаться на него.

### 3. Настройте локальный запуск

1. Установите актуальную LTS-версию Node.js.
2. Скопируйте `.env.example` в `.env`.
3. В `.env` укажите URL существующего Supabase-проекта и публичный ключ (`Publishable key` или старый `anon` key):

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_KEY
```

Не используйте `service_role` или `sb_secret_` ключи в клиентском `.env` и не отправляйте файл `.env` другим людям.

4. В терминале из папки `JanaMen` выполните:

```bash
npm install
npm run dev
```

5. Откройте адрес, который покажет Vite (часто `http://localhost:5173`).

### 4. Проверьте процесс с тремя аккаунтами

1. Зайдите как сотрудник, создайте тестовую заявку. Она должна иметь этап **Ожидает руководителя**.
2. Зайдите как назначенный руководитель, откройте заявку, оставьте комментарий и согласуйте. Она должна перейти к этапу **Ожидает HR**.
3. Зайдите как HR, примите итоговое решение. Должны сохраниться статус, комментарий, подпись и время. Если одобрен оплачиваемый отпуск, баланс в `profiles.annual_leave_days_remaining` должен уменьшиться на количество дней.
4. Проверьте отклонение руководителем отдельно: такая заявка завершается на первом этапе и не должна появиться в очереди HR для обработки.
5. Обновите страницу и убедитесь, что данные сохранены в Supabase.

Проверяйте все роли разными аккаунтами и убедитесь, что пользователь не может читать чужие заявки. Миграция устанавливает RLS-политики для `requests` и ограничивает доступ к `profiles`; не отключайте RLS для исправления ошибок.

### 5. Проверка кода

```bash
npm run lint
npm run build
```

- TypeScript и ESLint проверены после обновления исходников.
- Production-сборка в рабочей среде не была подтверждена: в доступных зависимостях отсутствовал Linux-бинарник Vite/Rolldown. Проверьте `npm run build` локально после `npm install`.
- SQL-миграция подготовлена, но не запускалась в вашем Supabase-проекте; её применение и проверку реальных политик нужно выполнить в вашей базе.

## Состав архива

- `src/App.tsx` — интерфейс ролей, отпусков и этапов согласования.
- `src/App.css`, `src/AssistantPanel.css`, `src/components/PulseCard.css` — бело-зелёная тема.
- `supabase/20261017_janapost_requirements.sql` — миграция базы данных и RLS/триггер для процесса согласования.
- `.env.example` — шаблон переменных окружения без секретов.
